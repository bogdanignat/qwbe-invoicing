# T-1480 step 5 (ops) — PostgreSQL backup and restore

Scope of this unit: the backup and restore **services** on PostgreSQL 16, their
archive format and the safety that surrounds them. The companion CLI already
exists (`standalone/ops/cli.ts`, `bin/qwbe-invoicing.ts`); the integration step
wires it to the API below. No second CLI was invented here.

Not in this unit and deliberately untouched: `RuntimeConfig` and the secret-file
read, the shipped compose files and `Dockerfile`, the HTTP and auth layers, the
boot-time SHARED maintenance lock, and every test outside backup/restore.

---

## 1 The API the CLI consumes

```ts
// standalone/ops/postgres-backup.ts
import type { Pool } from "pg"
import type { PostgresSettings } from "../storage/postgres-pool.ts"

interface BackupContext {
  readonly pool: Pool                  // the caller's; never created or ended here
  readonly settings: PostgresSettings  // what pg_dump / psql are told, password included
  readonly dataDirectory: string       // DATA_DIR: the content-addressed PDFs
}

const restoreTrustWarning: string      // the text the CLI must print before `restore --apply`
const planBackup:     (context: BackupContext) => Promise<{ readonly pending: ReadonlyArray<string> }>
const executeBackup:  (context: BackupContext, output: string) => Promise<BackupReport>
const planRestore:    (context: BackupContext, input: string) => Promise<{ readonly pending: ReadonlyArray<string> }>
const executeRestore: (context: BackupContext, input: string) => Promise<RestoreReport>

interface BackupReport {   // the fields the CLI already prints
  readonly dataDirectory: string
  readonly output: string
  readonly scanned: number
  readonly copied: number
  readonly failed: number
  readonly files: ReadonlyArray<string>
  readonly manifest: string
}
interface RestoreReport {
  readonly dataDirectory: string
  readonly input: string
  readonly scanned: number
  readonly restored: number
  readonly failed: number
  readonly files: ReadonlyArray<string>
}
```

`BackupContext` is its own type and not `RuntimeConfig`: a backup needs a pool,
the connection settings the subprocesses have to be handed, and the artifact
directory. Handing it the whole configuration would couple it to the shape of the
application's boot and make it untestable without one. The integration step builds
it from `runtimeConfig.pgSettings` and closes the pool in its own `finally`;
nothing here ends a pool.

`BackupReport.manifest` is a real path for a directory output and the member name
`manifest.json` for an archive — the staging copy is gone by the time the report is
read, and naming a path that no longer exists would be worse.

Failure classes, all exported from the modules that raise them:
`GuardRefusal` (`postgres-backup-guards.ts`) for a refused precondition,
`ArchiveRejected` (`postgres-backup-paths.ts`) for an unacceptable input,
`ToolFailure` (`postgres-backup-dump.ts`) for a child process, and
`RestoreInterrupted` (re-exported from the facade) for a restore that failed
part-way. The first two are the CLI's exit code 2 (guard refusal / invalid input),
the other two are 1.

`scanned`, `copied`, `failed` and `restored` are **invariants, not counters**:
every failure in these paths throws, so `copied`/`restored` always equal `scanned`
and `failed` is always 0. They exist because the CLI already prints them. A partial
outcome is never reported as success — it is `RestoreInterrupted`.

**For the integration step, two things to wire beyond the context:**
1. print `restoreTrustWarning` before `restore --apply` (§5 explains why);
2. `DATA_DIR` must already exist as a directory — these services refuse rather than
   create it, so the compose mount is load-bearing.

## 3 The decisions

**The application-stopped invariant is enforced, not documented.** `executeBackup`
and `executeRestore` take `pg_try_advisory_lock(1480, 1)` — the same key `migrate`
takes EXCLUSIVE and the running application holds SHARED for the life of its
process. It is a *try*: a refusal is immediate and bounded, because a maintenance
command that blocks behind a healthy application looks like a hang. One
checked-out client holds it for the whole operation, so no service below may take
it again on another connection (that is a self-deadlock, not re-entrancy). No
nested shared-lock transaction runs while the exclusive lock is held.
`pg_stat_activity` is read for the refusal message only: no backend is cancelled
and none is terminated.

**On failure the client is released destructively** (`client.release(error)`): it
may be mid-transaction or still hold a session lock, and the failing operation is
not in a position to know which, so it is discarded rather than returned to serve
a query. On success the lock is released explicitly first.

**Plain format, argued.** `--format=custom` adds a second compatibility surface
(the archive version negotiated with `pg_restore`) and permits a partial restore.
Plain SQL through `psql --single-transaction --set=ON_ERROR_STOP=1` is
all-or-nothing on the server, is checksummed and compressed by the archive anyway,
and lets a dry run read the whole artifact without `pg_restore` ever naming the
target. It also places triggers and foreign keys in the *post-data* section, after
the `COPY`s — so the row triggers of the real schema do not fire during the load
and the FK cycle is closed only once the data is in.

**`--schema=public` is not passed, and that is a defect found by running it.**
With it, `pg_dump` 16 emits `CREATE SCHEMA "public";` and the restore dies on a
fresh database with `ERROR: schema "public" already exists`. Editing the SQL or
dropping a schema are both out of bounds, so the scope is asserted on the source
instead: `assertSinglePublicSchema` refuses a backup of a database that has any
other user schema, which makes the whole-database dump and the `public`-only dump
the same artifact.

**Sessions.** `--exclude-table-data=public.browser_sessions` drops exactly the rows
and keeps the definition, so the restored schema does not drift and `migrate` and
`doctor` still recognise it. After a restore both halves are asserted: the table is
present and holds zero rows.

**Credentials.** `PGPASSWORD` is placed in the child's own environment object and
nowhere else — `process.env` is never written, the value never becomes an argument,
and the child's environment is built from scratch rather than inherited. Output is
captured, bounded at 64 KiB and redacted on every path, success and failure alike:
`redactSecrets` plus the password's own literal.

**Async subprocesses.** `spawnSync` would hold the event loop for the whole dump
while the maintenance lock is held. Every run is asynchronous and has a deadline
(10 minutes for a dump or a restore, 10 seconds for a version probe) enforced with
`SIGKILL`.

**Consistency.** The dump and the artifact copy run inside the one lock hold: a
document rendered between them would appear in the artifact tree with no row to
explain it.

**The backup is cross-checked against the database, not just collected.**
`assertArtifactsComplete` reads `object_key`/`sha256` from `invoice_artifacts` and
`proforma_artifacts` on the locked connection and requires every referenced PDF to
be in the backup with the digest its row claims. Without it, an unmounted artifact
volume produced `copied: 0, failed: 0`, exit 0 — a backup restoring a fiscal
database whose rows point at PDFs that do not exist. A file with no row is left
alone: a content-addressed orphan from a rolled-back render is harmless, a missing
one is not.

**`DATA_DIR` must already be a directory, and is never created.** `lstat`, not
`stat`, so a symlinked root is refused rather than followed. The failure this
prevents is silent and total: with the volume unmounted, a recursive `mkdir` would
have created the root inside the container, the PDFs would land on a filesystem that
dies with it, and the real volume would stay empty.

**The destination is refused before the dump, not after.** An archive path must not
exist; a directory path must be absent or empty — the same rule restore applies to
its target. Otherwise a ten-minute dump ran and the copy then died with `EEXIST`
half-way, leaving a mixture of an old backup and a new one that looked like a
backup.

**The writer is held to the reader's bounds.** `assertWithinLimits` runs after the
manifest is staged, so it covers every member the reader will see — the manifest
included — and adds the tar framing the reader counts (512 bytes of header per member,
padding to the block, 1024 bytes of end marker). It checks against the same
`ArchiveLimits` the reader enforces, so a 600 MiB
dump is refused at backup time instead of producing an archive this project's own
restore rejects with `member exceeds the size bound`. Note that the reader's 120 s
runtime bound is **per pass**, and verification adds a pass: a legitimate archive on
slow I/O needs `runtimeMillis` raised, not a smaller archive.

**A verification failure names what it left behind.** `writeArchive` has already
created and fsynced the output when verification runs, so every message says the
artifact at `<output>` is UNVERIFIED and must be moved aside or removed before a retry
— nothing is removed automatically. Without that, the retry met
`backup output already exists` with no hint that the file there is not a good backup.

**The artifact is read back and fsynced before success is reported.** The manifest
only ever proved the staging tree; `verifyArchive` re-reads the written archive
through the restore's own parser and compares every member digest with the manifest,
and the file and its parent directory are both fsynced. A truncated write, a late
`ENOSPC`, and any drift between the hand-written ustar headers and the reader now
fail at backup time.

**`--dbname` accepts conninfo; `pg` does not.** A database name containing `=` or
`://` would be read by `pg_dump`/`psql` as a connection string — host, port and user
overridable inside it — while the pool treats it as a plain name, so the guards
would be read on one server and the dump taken from another. `plainValue` refuses
any value that is not a plain token, and `assertTargetMatches` compares
`current_database()` on the locked connection with the name the tools are given.

**A deadline reads as a deadline.** An OOM kill, a `docker stop` and a ten-minute
dump all produced `signal SIGKILL`; the timeout now reports
`exceeded its N ms deadline and was killed`.

**Redaction happens before the cap, not after.** Capping first and stripping the
secret afterwards can leave a password prefix in the message when the literal
straddles the cut. `createRedactor` joins every chunk to a carry window at least as
long as the password, strips, and only releases what no later chunk can complete;
the 64 KiB cap is applied last.

## 4 The archive, and why it is parsed here

`tar` in the shipped image is BusyBox 1.37.0, and the step-0 probe recorded what
that means: a member whose name contains a newline is printed across two lines by
`tar -t`, warnings are interleaved into the listing, `../escape.txt` is extracted as
`escape.txt`, `/abs.txt` as `abs.txt`, a duplicate member is extracted twice and a
**symlink member is created as given**. A listing is therefore not parseable and an
extraction is not reviewable after the fact.

So the archive is read by `postgres-backup-tar.ts` / `postgres-backup-archive.ts`
— bounded streaming over `node:zlib`, no new dependency — and written by
`postgres-backup-writer.ts`, which fixes owner, group, mode and mtime so two
backups of the same content differ only where their data differs. No directory
member is written at all.

**Layout (the whole whitelist).** `manifest.json`, `database.sql`, and
`artifacts/sha256/<2 hex>/<64 hex>.pdf` — the object key
`standalone/documents/artifact-store.ts:17` produces. Anything else is not a
member; "unknown entry" is the default answer, not a catalogue of attacks.

**Diagnosed, not merely refused:** `artifacts/sha256/<ab>/.<sha256>.<uuid>.tmp`, the
name `standalone/documents/artifact-store.ts:42` stages an object under before
renaming it into place. A SIGKILL between the `open` and the `rm` leaves it, and the
generic refusal then blocked every backup with no instruction. The whitelist is not
relaxed for it — the refusal names the file and says it carries no document and can be
removed — and the check runs ahead of the 100-byte limit, which is a ustar constraint
that would otherwise have reported the 126-character name as "too long".

**Refused:** absolute names, `..` and `.` segments, empty segments, backslashes,
NUL and every other control character, names over 100 bytes, duplicates, the
`ustar` prefix field, a link target on a regular file, non-`ustar` magic, an
invalid header checksum, base-256 numeric fields, and every type flag other than
regular and the layout's directories — hard link, symlink, character and block
device, FIFO, contiguous, **PAX extended and global headers**, GNU long-name and
long-link records. PAX is refused outright rather than handled: a pax header
rewrites the name of the member that follows it, which is the indirection this
parser exists to deny. Also refused: truncation mid-block and mid-member, a stray
zero block, a missing end-of-archive marker, and data after it.

**Bounds** (`defaultArchiveLimits`, each one overridable): 4096 members,
512 MiB per member, 1 GiB expanded, 512 MiB compressed, 120 s runtime per pass. The
expanded bound is the decompression-bomb answer — an absolute cap, not a ratio. The
same bounds are applied to the writer, so a backup cannot produce an archive its own
restore refuses.

A corrupt or truncated gzip stream is reported as `ArchiveRejected`
("not a readable gzip stream"), not as zlib's `Z_BUF_ERROR`: a bad backup file is
unacceptable input (CLI exit 2), not an internal defect (exit 1). Only zlib failures
are wrapped — an `EACCES`, `EIO` or `ENOENT` keeps its own identity and stays exit 1,
because the read-back a backup performs reads a file the operator never supplied. The reader closes
the file, the gunzip and the source on every exit, including an early refusal, so
validating archives in a loop leaks no descriptor.

**Order, and the property it buys.** `inspectArchive` walks the whole stream and
writes nothing; `extractArchive` walks it again and writes. No byte of a rejected
archive ever reaches the filesystem, because the code that writes had not started.
Extraction opens every member with `wx` (`O_CREAT|O_EXCL|O_WRONLY`): it never
follows a symlink and never truncates. The staging tree is a `mkdtemp` under
`TMPDIR`, removed on every path.

**A directory input gets the same guarantees**, not a shortcut: the root is
`lstat`ed so a symlinked input is never walked; `readdir` reports entry types from
the directory itself; a hard link (`nlink > 1`) is refused because the content can
be changed through the other name; every file's `realpath` must equal its expected
path, which catches an intermediate component replaced between the walk and the
copy; and the copy opens with `O_NOFOLLOW` and compares `dev`/`ino` against the
walk. There is **no legacy shape** — an input that is neither `.tar.gz`/`.tgz` nor
a directory is refused with no fallback.

## 5 Restore: what it refuses, and what it never does

`planRestore` is read-only and lock-free on purpose: a dry run has to be able to
report that the target is populated while the application is still up. It validates
the whole input, reads the target's inventory, and never names the target to
`psql`. `executeRestore` re-reads every guard on the connection that holds the
exclusive lock — once before staging and once immediately before the first write —
so a database that filled up since the dry run is refused at the write, not at the
plan.

- **Empty database means empty.** Relations, routines and standalone types are
  counted across every non-catalogue schema, and extra schemas are counted too. An
  object this code has no name for is still an object.
- **Empty artifact tree means empty**, including files the layout does not know.
- **Nothing is ever deleted.** A populated target is a refusal with an
  instruction: create a fresh database and a fresh artifact volume.

**Order and partial-failure policy.** Artifacts are copied first and the SQL goes
in last, as one transaction. The SQL is the commit point: if anything before it
fails the target is still an empty database and no row can reference a PDF that is
not there.

A failure after the first write raises `RestoreInterrupted`, which states what
landed rather than leaving the operator to guess:

| field | meaning |
|---|---|
| `copyStarted` | a destination inside `DATA_DIR` was about to be opened — its content may be partial |
| `dataCopied` | at least one artifact file was written whole |
| `databaseCommitted` | the `psql --single-transaction` restore **committed** |
| `retrySafe` | always `false` |

`copyStarted` exists because `copyTree` creates its target with `wx` and only then
writes into it, and it does not unlink a partial file. An `ENOSPC` during the **first**
artifact therefore leaves a truncated `.pdf` behind, and the flag is set *before* the
destination is opened rather than after the copy returns — otherwise that case
reported "no artifact file was written", the operator read "nothing happened", retried,
and met `requires an empty artifact directory`. When `copyStarted` is true and
`dataCopied` is false the message says the size is unknown rather than claiming zero.

`retrySafe` is false by construction: this command never writes on top of existing
state, so the only resumption is **a fresh database and a fresh artifact volume**.
Nothing is deleted to make that possible — not by this code, and not as advice.
`databaseCommitted: true` is the honest case the old code hid: a check that fails
after the commit (`assertSessionsEmpty` on a tampered dump) reports a restored
database, because nothing can take the commit back.

The `--apply` / production confirmation stays in the CLI the integration step
wires; these services refuse on their own preconditions and never report a false
"empty".

### The trust boundary

`database.sql` is **executed**, by `psql`, as the application's own database role.
Everything this unit checks is about the archive as a filesystem object — member
names, types, sizes, digests, manifest consistency, tool majors. None of it inspects
the SQL, and the digests cannot help: they live inside the same archive as the file
they describe, so they prove integrity and **not** authenticity. Anyone able to
write the archive recomputes them.

So the model is explicit: **restore only from a source trusted as much as the
database itself.** An archive an attacker can write is an archive whose SQL runs with
the role's full rights — `COPY ... FROM PROGRAM` if the role has it, redefined
trigger functions that undo the `*_no_update`/`*_no_delete` immutability the fiscal
correctness rests on. `restoreTrustWarning` is exported from the facade for the CLI
to print; signing the manifest with a locally held key would turn this into an
authenticity check and is deliberately **out of scope** — no HMAC, no key management
is implied anywhere in this code.

## 6 Verification

Rig: `compose.pg-backup.yaml` — PostgreSQL 16 on tmpfs, no published port, no
volume, its own project name, `scram-sha-256` with a rig-only password so the
subprocess credential path is really exercised (the adapter rig's `trust` would let
it pass while broken). `postgresql16-client=16.15-r0` is installed into the test
container at start, because the shipped `Dockerfile` belongs to the integration
step; `apk`'s own exit status is read and the major is asserted from the tool.

```sh
docker compose --file compose.pg-backup.yaml run --rm backup   # 32 tests
docker compose --file compose.pg-backup.yaml down              # no volume, no -v
scripts/verify-docker.sh run "node --test standalone/ops/postgres-backup-archive.test.ts"
scripts/verify-docker.sh run "pnpm typecheck"
scripts/verify-docker.sh run "pnpm lint && pnpm gate:size && pnpm gate:boundaries"
```

Observed: `pg_dump (PostgreSQL) 16.15`, `psql (PostgreSQL) 16.15`, server
`server_version_num` major 16. **32/32 pass.** The roundtrip asserts the restored
database matches the source on tables, triggers, functions and ledger rows, that
`browser_sessions` is present with zero rows, and that the restored PDF is
byte-identical by sha256.

Beyond the roundtrip, the suite proves the edges the first review found open: a
missing `DATA_DIR` refused and not created; a referenced PDF absent, and one with a
digest its row does not claim; a destination that already exists or is not empty,
refused before the dump; a 1 ms deadline reported as a deadline with the lock intact
afterwards; a second maintenance operation on the same pool refused; a fault
injected between two artifact copies reporting `dataCopied: true` /
`databaseCommitted: false` with the retry refused; a tampered dump that commits and
then fails `assertSessionsEmpty`, reporting `databaseCommitted: true`; the redactor
against a secret split across chunks and across the output cap; and 60 consecutive
rejections of a hostile archive with no descriptor growth.

The last pass added, and closed with observation rather than argument: the write guard
refused with injected small bounds while the same backup succeeded with the defaults
and left no artifact behind on refusal; an interruption at the *first* artifact
reported `copyStarted: true, dataCopied: false`; an `ENOENT` stayed an `ENOENT` instead
of becoming an archive refusal; the leftover-temp diagnosis fired on the real
126-character name; the framing arithmetic was checked at the exact boundary (2047
refuses, 2048 passes, and the reader agrees at 2048).

**Tar interop, previously a standing gap, is now observed in both directions.**
BusyBox `tar -tzf` lists `manifest.json` and `database.sql` from an archive this
writer produced, and an archive produced by `tar -czf` — padded to its 10240-byte
record — is accepted by this reader.
